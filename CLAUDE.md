# Hexfinity

Blender 5.1+ extension that generates a grid of interlocking hexagonal terrain tiles with per-corner height control.

## Ignore the ideas.md file. Only containing notes

## Run / build

- **Tests** (uses Blender's bundled Python; ten modules below — `mesh_builder.py`, `map.py`, `manifold_check.py`, `procedural_surfaces.py`, `subdivision.py`, `tile_export.py`, `tree_pads.py`, `terrain_pads.py`, `face_select.py`, `bambu_slicer.py` — are bpy-free so they import in plain CPython). Blender's bundled interpreter doesn't ship pytest, so install it once first:
  ```
  "C:\Program Files\Blender Foundation\Blender 5.1\5.1\python\bin\python.exe" -m pip install --user pytest
  "C:\Program Files\Blender Foundation\Blender 5.1\5.1\python\bin\python.exe" -m pytest tests -v
  ```
- **Build / deploy**: `deploy.ps1` — zips to `dist/`, optionally junctions source into Blender's user extensions for live dev.
- **Extension manifest**: `blender_manifest.toml` (Blender 5.x format — not the legacy `bl_info` dict).

| `properties.py` | `HexFinityMapProperties` (scene-level) + `HexFinityProperties` (per-tile P1–P6 corner heights, plus `is_baked` — a UI-only flag set/cleared by `operators.HEXFINITY_OT_bake_tile`/`HEXFINITY_OT_unbake_tile`; nozzle's items depend on the chosen printer, filament/quality's depend on the resolved printer+nozzle combo, via the lenient `bambu_slicer.resolve_machine`). The sentinel/placeholder item's id is `"NONE"`, not `""`, despite `""` being `bambu_slicer.py`'s own "not set, auto-detect" convention for these same four fields (mirrored by `scripts/slice_tiles_settings.json`) — assigning an empty-string identifier to a dynamic-items `EnumProperty` raises `enum '' not found in (...)` (confirmed by hand: Blender silently excludes an empty-string item from a callback-based enum's valid set at assignment-validation time, even though it's right there in the returned list) — `_slice_setting_value(enum_value)` is the one place that translates `"NONE"`/`""` (Blender enum id) to/from `""` (`bambu_slicer.py`'s convention), called by every read site (`_persist_slice_settings`, `operators.HEXFINITY_OT_export_and_slice.execute()`'s settings-dict construction) and cascade-reset (`self.nozzle = _SLICE_NONE_ID`, never `''`). A module guard `_SLICE_FILLING` (save/restore the previous value, not just `False`, mirroring `_REGION_FILLING`/`_PATH_FEATURE_FILLING` below) makes a printer change's cascade — reset `nozzle` to NONE, which itself resets `filament`/`quality` to NONE — persist to the shared settings JSON exactly once, with the fully-resolved final state, via `_persist_slice_settings`/`bambu_slicer.save_settings_fields(bambu_slicer.blender_settings_path(), ...)` (a `None` path — no sibling `scripts/` dir, e.g. an installed extension — or any `OSError` is silently swallowed). `sparse_infill_density`/`sparse_infill_pattern` are a plain `IntProperty`/static-items `EnumProperty` (their bounds/items are fixed constants, not install-dependent) but still persist on every change the same way. `adaptive_layer_height` is a plain `BoolProperty` (default off) persisted the same way — injected onto the flattened process config as Bambu's own `adaptive_layer_height` bool (`"1"`/`"0"`) by `bambu_slicer.write_full_configs`, same layer `sparse_infill_density`/`sparse_infill_pattern` land on. `delete_stls_after_slicing` (default on) is the one field that's Blender-only, never part of the shared JSON schema), `HexFinityProperties.surface_texture` — a `PointerProperty(type=HexFinitySurfaceRegion)` singleton reusing the *same* region type as `surface_regions` rather than a new PropertyGroup, so its own `surface_type`/`feature_mm`/`depth_mm`/`regularity`/`direction_deg` fields and their existing `_on_region_update`/`_on_region_type_update` callbacks work unchanged (`self.id_data` resolves the owning Object regardless of nesting); `points` is simply never populated on it, so it always marshals to a whole-tile (no-`polygon`) region — the panel's "Surface Texture" box (see `panel.py`), the base layer under Draw Area/Path Feature. `_default_region_name` special-cases this singleton (checked after the `surface_regions` loop, via pointer-equality against `tile.surface_texture`) to return `"Surface Texture"` instead of an "Area N" name. `NONE` (the default) is off, same as any other region. And `HexFinityPathFeature` (per-tile: `name`/`feature_type` enum (`SIMPLE`/`GRAVEL`/`PAVED_ROAD`)/`width_mm`/`depth_mm`/`repeat_mm`/`texture` enum + `points` reusing `HexFinitySurfacePoint`. Every field has an `update=` that rebuilds the tile — Path Feature auto-carves on any edit, no manual gate. `texture` is set by `feature_type`'s autofill but is no longer drawn in the panel — `feature_type` alone determines it, `panel.py` never exposes its own dropdown for it. `feature_type`'s `update=_on_path_feature_type_update` is the sole autofill trigger: guarded by `_PATH_FEATURE_FILLING` (mirrors `_REGION_FILLING`), it calls `path_features.apply_type_defaults()` to set `width_mm` (a direct `man_height_mm` factor, model-scale-aware) plus fixed-literal `depth_mm`/`repeat_mm` (NOT scaled by man height) and pick a default `texture`, sets a `_default_path_feature_name()`-derived name if still empty, then rebuilds once — `path_features._commit_feature` relies on this single assignment firing correctly *even when the type equals the property's own Blender-level default*, since Blender's `update=` still fires on a same-value Python assignment). A fourth `feature_type`, `RIVER`, has its own field shape — no `texture`/`repeat_mm` — instead adding `depth_levels` (an int, the map's Level unit rather than mm — `path_features.path_specs()` resolves it to mm fresh every rebuild via the current `level_height_mm`, never resolved-once like `width_mm`), `embankment_angle_deg` (plain degrees, not the `ANGLE` subtype, same convention as `direction_deg`/`angle_threshold_deg`), `embankment_variation_mm` (resolved once from `man_height_mm` at type-select, like `width_mm`), `river_bottom_style` (`NONE`/`TESSENDORF_FFT`, the flat-vs-rippled channel bed), and `preserve_edge` (a `BoolProperty`, default `True`, mirroring `HexFinityBrushProperties.preserve_edge` — damps the carve near the rim when on, or carves right to the rim with a deterministic embankment when off). A fifth `feature_type`, `SEGMENT`, is the odd one out: it carries none of the above fields (its own `_on_path_feature_type_update` branch skips `apply_type_defaults()`/the default-name fill entirely) and instead adds `segment_run_id` (a str, groups every hex's entry belonging to one continuous `segment_path.HEXFINITY_OT_start_segments_path_draw` placement run) and `segment_piece` (a `PointerProperty(type=bpy.types.Object)`, the actual placed/clipped mesh Object for *this* hex — see `segment_path.py`'s row). A placed segment is a real mesh object, not a carved groove, so `path_features.path_specs()` never needs to special-case it: its `points` collection is simply always left empty, which is already `path_specs()`'s existing skip condition for "fewer than 2 points" |
| `mesh_builder.py` | **bpy-free** — `build_hex_tile()`; top surface is Loop subdivision (via `subdivision.py`) over a 13-vertex control mesh (`C`, `P1..P6`, `Q1..Q6`) with sharp-tagged rim edges — supersedes the earlier Coons-patch construction; side walls; interlock tabs/holes. Optional `flora_pads`/`terrain_pads` kwargs (each a list of `{"x","y","radius_mm","blend_mm"}` dicts, `terrain_pads` entries also carrying an explicit `"z"`) are concatenated and locally refine+flatten the top surface via a single `tree_pads.refine_and_flatten` call, between the brush/procedural-surface displacement loop and top-face emission; collects `protected_edges` (the rim chains) so refinement can never split a rim edge. The two kwargs must be merged into one call, not two sequential ones — `refine_and_flatten` samples every pad's target *before* any flattening happens, so nearby flora/terrain pads sampling each other's post-flatten surface would double-blend where footprints overlap. Optional `flora_notches`/`flora_notch_warnings`/`flora_notch_ok_indices`/`flora_notch_heights` kwargs, applied strictly after the merged pad pass, drill a blind cylindrical pin socket via `tree_pads.cut_notches`; `flora_notch_heights` receives `{index: pad_z}`, the exact pre-drill flat height per successful cut, so `flora.py` can seat a tree/pin there directly instead of raycasting into the hole it just cut. `FLORA_PIN_*`/`FLORA_NOTCH_*` constants (pin diameter 2mm, notch depth 10mm, tolerance 0.2mm — all hardcoded, independent of `man_height_mm`) live alongside `TAB_*` and are imported by `flora.py` as the single source of truth for both the tile-side socket and the tree-side pin object. Optional `path_features` kwarg (a list of per-drawn-line dicts, one per Path Feature line, each tagged `"kind"`: `"texture"` — SIMPLE/GRAVEL/PAVED_ROAD, `{"points","width_mm","depth_mm","blend_mm","repeat_mm","pixels","tex_width","tex_height"}` — or `"river"` — RIVER, `{"points","width_mm","depth_mm","embankment_angle_deg","embankment_variation_mm","river_bottom_style","local_subdiv","seed"}` plus `"pixels"`/`"tex_width"`/`"tex_height"`/`"ripple_patch_mm"` when rippled) is partitioned by `"kind"` (missing/old-shaped entries default to `"texture"`) and applied via two separate calls, `tree_pads.refine_and_displace_along_path` (texture group) then `tree_pads.refine_and_carve_river` (river group, so it wins if the two ever overlap), strictly *after* the merged `flora_pads`/`terrain_pads` flatten pass and before `flora_notches` — a path/river carves into whatever the pad-flatten layer already produced, matching the topmost position in the user-facing Water/Land/Draw Area/Path Feature layer stack (see `tree_pads.py`'s row for the actual displacement math). Optional `baked_extra=(extra_verts, extra_faces, prefix_overrides)` (see `operators.HEXFINITY_OT_bake_tile`) short-circuits all four of the above — no `tree_pads` call at all — and instead, right after the top-vertex brush/region loop, applies `prefix_overrides` (`{top_vertex_index: z}`) to the freshly-generated top-vertex prefix and appends `extra_verts`/uses `extra_faces` verbatim, exactly where the live pad/notch/path pipeline would have left them; `surface_regions` is unaffected, since baking never touches it — `top_displacement` (brush) *is* affected, but only in the sense described next. Optional `bake_capture` (an output-only dict) is the inverse: given on a *live* build (i.e. `baked_extra=None`), it's filled in with `num_top`/`extra_verts`/`extra_faces`/`prefix_overrides` — everything `operators.rebuild_tile` needs to freeze that build's pad/notch/path result into a `baked_extra` tuple for a later call; `prefix_overrides` is computed by diffing each top-vertex's z immediately before vs. after the pad/notch/path section runs, since `tree_pads.refine_and_flatten`/`refine_and_displace_along_path` mutate pre-existing (not just newly-appended) vertices in place. **Terrain-brush priority pass**: after that whole section (live recompute or `baked_extra` replay, either way), `build_hex_tile` re-applies `top_displacement` a second time, but only at whichever original-index vertices `prefix_overrides`/the diff says pad/terrain/path/notch actually changed (`touched_indices`) — everywhere else already got the brush's contribution once, from the combined brush+region loop above, so re-adding it there would double it. This is what makes a hand-painted stroke win over a pad/path/notch recompute in its own footprint (e.g. a tree's flatten-base pad no longer comes out perfectly flat if it overlaps a painted bump) without inflating brush strength tile-wide — see `test_top_displacement_wins_over_pad_without_doubling` in `tests/test_mesh_builder.py`. |
| `tree_pads.py` | **bpy-free** — `sample_surface_z()` (barycentric height lookup), `_iteratively_refine()` (the marked-edge adaptive subdivision loop shared by `refine_and_flatten` and `cut_notches`), and `refine_and_flatten()`: per-edge adaptive triangle refinement (crack-free by construction, capped at `MAX_LEVELS`) plus a per-vertex lerp-toward-pad-height flatten with a rim-edge-distance fade so a pad near the rim shrinks rather than desyncing the seam with the neighbouring tile. A pad dict may carry an explicit `"z"` target height instead of the default sampled-from-surface one — flora pads omit it, `operators.terrain_pad_specs` sets it to the terrain object's own target height, since a terrain plateau must move the surface to an externally-dictated height rather than just flatten wherever it already is (this is the *sole* mechanism that deforms a hex to match a terrain object — there is no separate raycast displacement layer). New vertices are always appended after the caller's existing vertex range, never inserted, so the brush displacement-layer indices stay valid. `cut_notches()` drills a blind cylindrical socket per notch spec: forces its own deeper refinement (`NOTCH_MAX_LEVELS`) than a pad's own flatten produces, removes triangles fully inside the notch radius, walks the hole's boundary into a loop via `_boundary_loop()` (rejecting pinch points/multiple loops via a boundary-edge-degree check), snaps the loop onto an exact circle, and builds the wall+floor by reusing the removed region's own triangulation (remapped down) rather than a fresh fan — so no interior vertex is ever orphaned. Skips a notch (appending a reason to `warnings`, recording successes in `ok_indices` and their pre-drill flat height in `resolved_heights` as `{index: pad_z}`) rather than risking a corrupt mesh when the local mesh is too coarse, the boundary is irregular, it reaches the rim, or the tile is too thin (`FLORA_NOTCH_MIN_FLOOR_MM`). Imported lazily from inside `mesh_builder.build_hex_tile` (only when `flora_pads`/`terrain_pads`/`flora_notches`/`path_features` is non-empty) to avoid a circular import, since `tree_pads.py` itself imports from `mesh_builder`. A third refine+apply strategy sharing `_iteratively_refine`, for Path Feature: `curvilinear_coords(x, y, points)` (nearest-segment projection of a point onto an open polyline → `(s, t)` = arc-length-along/signed-perpendicular-distance-from the centerline — clamped past the polyline's endpoints, not wrapped), `sample_grayscale(pixels, width, height, u, v)` (bilinear sample of a flat row-major grayscale array; `u` wraps, `v` clamps), and `refine_and_displace_along_path(verts, faces, protected_edges, paths, diameter_mm, base_thickness_mm)`: derives its own refinement pad-chain per path (small `{x,y,radius_mm,blend_mm}` circles stepped along the polyline, same shape `_iteratively_refine` already consumes) internally rather than requiring the caller to supply one, then for every vertex within `width_mm/2 + blend_mm` of a path samples `(s, t)` → texture `(u, v)` (`u = s / repeat_mm`, `v = 0.5 + t / width_mm`) and applies `offset = (gray - 0.5) * 2 * depth_mm` weighted by the same radial+rim-fade blend shape `refine_and_flatten` uses — **heightmap convention: white = +depth_mm (raised), mid-gray = unchanged, black = -depth_mm (carved)**. A path dict's `pixels` may be `None`, sampling as a constant `0.0` (solid black) — a uniform full-depth groove, not a no-op, so a line is visibly functional before any texture asset exists. Multiple overlapping paths apply sequentially, each adding its own weighted offset to whatever the previous one left (same shape as `refine_and_flatten`'s per-pad lerp loop). The per-path-independent-levels refinement loop both this function and River's carve need is factored out as `_refine_corridors_with_own_levels(verts, faces, protected_edges, refine_specs)`, shared by both. A fourth refine+apply strategy, for River: `refine_and_carve_river(verts, faces, protected_edges, rivers, diameter_mm, base_thickness_mm)` combines `refine_and_flatten`'s absolute lerp-toward-target shape (right for a structural reshaping feature that must stay geometrically consistent regardless of ambient terrain noise) with `refine_and_displace_along_path`'s curvilinear `(s, t)` sampling frame, rather than that function's additive/texture-driven approach (right for a shallow surface groove, wrong for a channel that must have a constant bed depth and constant-angle banks). Per vertex: `half_bed = width_mm/2` is the flat bed, constant regardless of angle — embankments extend *outward* beyond it, never inward; `nominal_run_mm = depth_mm / tan(embankment_angle_deg)` (no special-casing at 90° — `tan(90°)` is numerically ~1.6e16 in floats, so the run already comes out ~0); a per-side `procedural_surfaces._value_noise` term (`embankment_variation_mm`) perturbs that run so the bank line wanders naturally; the cross-section weight is **linear**, not smoothstep, in the embankment ramp — deliberately different from every other function in this file, since a constant-angle slope is geometrically a straight line — while a `preserve_edge` flag (default `True`, mirroring `HexFinityBrushProperties.preserve_edge`) gates whether the mandatory `rim_edge_distance` fade applies at all — on, the fade uses the local embankment run as its own fade distance, the same seam-matching invariant every pad/path/brush displacement relies on by default; off, the fade is skipped entirely (the carve reaches full depth right up to the rim vertices) and the embankment-variation noise term is instead separately faded to exactly 0 at the rim (over the `max_reach_mm` band) so the bank position at the very edge is the deterministic `nominal_run_mm`, letting a matching river on the neighbouring tile (same edge waypoint, same width/depth/angle, also `preserve_edge` off) continue it directly. The target height is `reference_z(s) - depth_mm`, where `reference_z` is the pre-carve surface sampled once along the centerline via new helpers `_point_at_arclength`/`_sample_centerline_heights`/`_interp_table` (mirrors `refine_and_flatten`'s up-front pad-height sampling). When a river's `river_bottom_style` is `"TESSENDORF_FFT"`, a static ripple — baked from Blender's Ocean modifier by `path_features.py`, normalized to `[0,1]` and sampled here via the same unmodified `sample_grayscale` — is added to the bed target strictly within `d <= half_bed`, tapered to 0 at the bed/embankment boundary (`RIVER_RIPPLE_AMPLITUDE_FACTOR` scales it) so it stays continuous with the (always ripple-free) ramp. Continuing a river into a neighbouring tile is therefore one of two workflows (lower the shared corner Level(s), or turn `preserve_edge` off on a matching pair of rivers) — not something this function special-cases beyond honouring the flag (see `path_features.py`'s row) |
| `terrain_pads.py` | **bpy-free** — `cluster_grid_hits()`: tiles a boolean "under the model's flat base" grid (built by `operators._terrain_pad_grid_hits` via raycasting) into small circular pad specs by grouping cells into `block_cells x block_cells` blocks and fitting one circle per non-empty block from that block's own member cells. Deliberately block-tiling rather than one bounding circle per 4-connected region: a footprint that wraps around a hole (e.g. a ring) is still one connected region, but its centroid — and a single circle's full radius — can land squarely on the hole; block-tiling bounds any one pad's span to roughly `block_cells` grid cells, the same kind of grid-resolution limit the raycast sampling and notch-drilling code already live with elsewhere. Consumed by `operators.terrain_pad_specs`, which stamps each resulting pad with the terrain object's `snap_damp_mm` as `blend_mm` and its computed `target_z` as `"z"`, ready for `mesh_builder.build_hex_tile`'s `terrain_pads` kwarg |
| `map.py` | **bpy-free** — odd-q offset math, `SHARED_CORNERS` table, `EDGE_DIRECTIONS` (a 6-tuple, `EDGE_DIRECTIONS[i]` the one neighbour direction bordering the edge from `corner_xy(i)` to `corner_xy((i+1)%6)` — the single direction common to `SHARED_CORNERS[i]` and `SHARED_CORNERS[(i+1)%6]`, hand-derived and cross-checked against `SHARED_CORNERS` by `test_edge_directions_consistent_with_shared_corners` in `tests/test_map.py`; | `bambu_slicer.py` | **bpy-free** — Bambu Studio CLI slicing mechanics: `find_bambu_executable`/`profiles_dir` (locate the install), `build_profile_index`/`flatten_profile` (resolve `resources/profiles/BBL`'s partial `inherits`/`include`-based presets into full configs), `list_printers`/`list_processes`/`list_filaments` (enumeration for dropdowns/validation), `read_manifest`/`read_flora_manifest`/`tile_counts`/`count_for` (per-tile print quantities from `manifest.json`/`flora_manifest.json`), `slice_jobs(folder)` (bpy-free, independently tested — groups a folder's STLs into `_SliceJob(stl_paths, out_stem, count)` plates: a hex position with finalized flora — per `flora_manifest.json` — gets one job combining its tile STL with every one of its tree STLs, `count=1`, named `hex_qNN_rNN` after the *position* rather than the tile file's own name, since that file may be a dedup-shared one (`tile_export.py`'s dedup contract) also used verbatim by other, flora-less positions; every other tile STL keeps the original one-job-per-file/print-count behaviour. A plain tile file's own bare name can coincide with a *different* flora position's position-based name — `is_custom_tile` doesn't look at flora at all, so a flora-planted tile is very often otherwise-plain — `slice_jobs` disambiguates with a `_2`/`_3`/... suffix rather than letting two jobs collide on one output filename; a `*.stl` outside the manifest entirely still gets its own job, count 1, matching pre-grouping behaviour), `gcode_name`/`threemf_name`/`extract_plate_gcode` (output naming + pulling plain G-code out of the CLI's only output format, a `.gcode.3mf` zip), `write_full_configs`/`build_slice_command`/`slice_one`/`slice_folder` (the actual `subprocess` slicing, one call per *job* — `build_slice_command`/`slice_one` accept either a single STL path or an iterable, passing every path from a job onto one `--arrange 1` call so Bambu Studio auto-arranges a job's STLs onto one shared plate; It adds a `LATTICE` modifier (`LOCK_MODIFIER_NAME`) pointing at the new lattice, sets `hexfinity_terrain.has_conform_lattice` (mirrors `HexFinityProperties.is_baked`'s UI-only-flag convention), and switches straight into Edit Mode on the lattice so the user can Tab in and drag control points, watching the modifier deform the mesh live. `HEXFINITY_OT_apply_conform_lattice` ("Apply", `poll` requires `_resolve_conform_edit` plus `operators._terrain_object_within_own_hex` — deliberately NOT `_hex_split_candidates`, the looser pre-filter `HEXFINITY_OT_split_terrain_by_hex` uses, since used directly here it would false-positive on almost any terrain object filling a meaningful part of its own hex) bakes the current deformation (`modifier_apply`, guarded by an explicit Object Mode check first), removes the lattice, clears `has_conform_lattice`, and — mirroring `HEXFINITY_OT_generate_terrain_plateau`'s own invalidate-then-rebuild pattern, since a `modifier_apply` bake is exactly the "mesh edit at an unchanged transform" case that pattern's docstring already calls out as invisible to the signature-based cache — deletes the parent tile's `hf_terrain_pads`/`hf_terrain_pads_sig` cache keys and calls `operators.rebuild_tile` so the hex's own plateau reflects the newly-conformed shape. `HEXFINITY_OT_cancel_conform_lattice` ("Cancel") is the discard path: removes the modifier *without* applying it, removes the lattice, clears the flag — no rebuild, since the mesh itself was never touched. Both Apply and Cancel resolve their target via `_resolve_conform_edit(context)`, which works whether `context.active_object` is the terrain mesh or its lattice (the normal case once Tab has made the lattice active) and self-heals — clearing a stuck `has_conform_lattice` — if the modifier/lattice was deleted by hand via the Outliner; `conform_target_for_lattice(lat_obj)` is the one-way half of that resolution `panel.py` calls directly to decide whether to draw the Apply/Cancel box when a Lattice object is active. `HEXFINITY_OT_split_terrain_by_hex`'s `poll` requires `not has_conform_lattice` instead of the old `not is_locked`, since duplicating the object per hex piece mid-edit wouldn't sensibly carry the lattice/modifier along |

## Invariants — preserve when editing

- **bpy-free rule**: `mesh_builder.py`, `map.py`, `manifold_check.py`, `procedural_surfaces.py` (incl. all scatter geometry math), `subdivision.py`, `tile_export.py`, `tree_pads.py`, `terrain_pads.py`, and `bambu_slicer.py` must never import `bpy`. That isolation is what lets the pytest suite run against Blender's bundled Python without launching Blender. `regions.py`/`scatter.py`/`flagstones.py`/`flora.py`/`path_features.py` themselves do import `bpy` — keep object/raycast/boolean/STL-import/image-loading code there, and keep any pure-math helpers extracted into it bpy-free (e.g. `path_features.py`'s snap-point geometry lives in `map.py`, and its curvilinear/texture-sampling math lives in `tree_pads.py`, instead).
- **Manifold guarantee**: every built tile is validated by `assert_two_manifold()`; failure raises loudly so silent mesh corruption is caught.
- **Tab geometry is hardcoded** in `mesh_builder.py` (`TAB_WIDTH_MM`, `TAB_HEIGHT_MM`, `TAB_DEPTH_MM`, `TAB_HOLE_TOLERANCE_MM`) — these constrain minimum base thickness and diameter. Check the constants before changing related values.
- **Corner sync**: `SHARED_CORNERS` in `map.py` defines which neighbours share each corner; `on_global_update` propagates per-corner writes across seams.
- **River cross-tile continuity is a workflow, not code**: by default (`preserve_edge=True`), like every other pad/path/brush displacement, a River path feature's carve fades to exactly 0 at a tile's rim edge (`tree_pads.refine_and_carve_river` reuses the same `rim_edge_distance` mechanism, with the local embankment run standing in as the fade distance) — this is load-bearing for the interlocking-seam guarantee (two independently-built neighbouring tiles' shared edges must match) and must not be special-cased away for rivers. A river meant to continue into a neighbouring tile this way needs the shared corner Level(s) at the crossing edge lowered to at least the river's own `depth_levels`, on both tiles (the per-corner Level sliders already auto-propagate to the shared neighbour corner) — this makes the ambient terrain the rim-fade reverts to already sit at the river's bed depth, so the seam reads as continuous. **`preserve_edge=False`** is the deliberate escape hatch: it's a per-river, user-opt-in override (mirroring the Terrain Brush's own Preserve Edge) that skips the rim-fade for that one river and forces its embankment-variation noise to 0 right at the rim, so its carve reaches the rim vertices at a fully deterministic depth/bank position — safe because disabling it never affects the tile's own manifold validity (only cross-tile visual/print alignment, which the user is knowingly trading away), and the burden of actually matching up is on the user drawing equivalent rivers (same edge waypoint, same width/depth/angle) on both sides.
- **Scatter kind contract**: a `scatter` `Surface` has `generator=None`, so `surface_offset()` returns `0.0` (zero displacement) and the `GENERATING` test fan-out (`s.generator is not None`) excludes it — do not give a scatter surface a generator. Scatter objects are regenerated by `scatter.purge_scatter` + `sync_scatter` on every `rebuild_tile`; the seating raycast must run *after* the tile mesh is assigned and the depsgraph updated so it samples current (not stale) geometry.
- **Brush displacement layer**: top-surface verts are registered first in `build_hex_tile` (indices `0 .. num_top-1`), and `num_top` depends only on `smoothness_passes + resample_density` (see `top_vertex_count`, pinned to the builder by `test_top_vertex_count_matches_builder`). `obj["hf_brush_disp"]` is a `float[num_top]` z-offset layer, re-sampled on every rebuild; `rebuild_tile` drops it when the length no longer matches `num_top` (a subdivision/resample change), which is the intended "paint survives height edits only" contract. It is applied **twice** inside the builder, by design, never doubled in net effect: once combined with the region value, before any pad/terrain/path/notch work (so those stages see a Z-consistent starting surface — see the next bullet for why that matters), then a second time at the very end, re-asserted only at whichever original-index vertices pad/terrain/path/notch actually changed (`touched_indices`, derived from the same pre/post-pad diff `bake_capture`'s `prefix_overrides` uses) — so a hand-painted stroke always wins over one of those recomputing its own footprint, on every rebuild, without inflating brush strength anywhere untouched. Both applications clamp to `>= base_thickness_mm`.
- **Tree-pad vertex ordering**: `tree_pads.refine_and_flatten` only ever *appends* new vertices — never inserts — so every index below the caller's original vertex count stays valid. `mesh_builder.build_hex_tile` calls it once (on `flora_pads` + `terrain_pads` concatenated) strictly between top-vertex displacement and the "Bottom of the tile…" section, so pad-refinement verts land at indices `>= num_top` and strictly before any bottom/side/tab vertex `add_vert` registers — planting/unplanting a tree, or a terrain object's plateau appearing/disappearing, therefore never disturbs `top_vertex_count()` or `hf_brush_disp`. Refinement must also never split a rim edge (`protected_edges`, collected from the same `rim_chains` the side wall's `top_rim_key` depends on) or the wall n-gon desyncs. `tree_pads.cut_notches` (run after the merged pad pass, only when finalizing flora) keeps the same append-only contract for its wall/floor verts, but *does* mutate existing vertices in place: a socket's boundary-loop vertices get their (x, y) snapped onto an exact circle (z untouched), and any genuinely-interior vertex of the drilled region sinks straight to the socket floor (z changed, same index, reused for the floor mesh so nothing is ever orphaned) — both safe since the brush layer only ever reads/writes Z by index. **The brush's first application must stay where it is** (combined with region, before any of this refinement runs): `tree_pads._retriangulate`'s quad-split diagonal choice (the `n_marked == 2` case) picks between two candidate diagonals by comparing their 3D lengths (`_dist3`, Z included) — if some vertices carried the brush's contribution at that point and others didn't, the resulting Z-inconsistency can flip which diagonal gets chosen between an otherwise-identical painted vs. unpainted build, silently producing different topology (not just different heights). A uniform (or absent) shift across every vertex feeding a given comparison never flips it, which is exactly what keeping the brush in the early, universal pass guarantees.
- **Layer order / Path Feature displacement**: the user-facing mental model is a stack — Water, Land Surface, Draw Area (regions), Path Feature, **Terrain Brush** — and the pipeline reflects it in stages. Regions (`_surface_offset_for_regions`) **sum** every region's masked contribution across the *whole tile* in a single order-independent pass (a future Water/Land Surface slots in here, as new `procedural_surfaces.SURFACES` entries authored via the existing whole-tile-region mechanism — no new plumbing), combined with the brush's own contribution in that same early pass (see "Brush displacement layer" above). `combined_pads` (flora+terrain) then locally flattens on top of that. `path_features` (`tree_pads.refine_and_displace_along_path`) carves/raises on top of whatever the pad pass left. The **Terrain Brush** is the topmost layer: its priority re-assertion pass (above) runs last, after all of the above, winning over whatever a pad/path/notch just computed in its own footprint — e.g. a tree's flatten-base pad, or a river bed, that overlaps a previously hand-painted area will no longer come out perfectly flat/at its computed depth; the old paint rides on top of it, every rebuild, until repainted. Same append-only vertex contract as the pad pass (new verts land after the existing range, never inserted) — the brush's re-assertion only ever touches the original `0 .. num_top-1` indices, never a pad/path/notch-appended vertex. Heightmap convention for any future texture-driven displacement (Path Feature now, Water/ground-texture later): **white = raised, mid-gray = unchanged, black = carved** — `offset = (gray - 0.5) * 2 * depth_mm`.
- **Bake**: `hexfinity.bake_tile`/`hexfinity.unbake_tile` (see `operators.py`'s row for the mechanics) freeze flora/terrain pads, flora notches, path-feature carving, and the terrain brush into id-properties replayed instead of recomputed — displacement regions (Draw Area/Surface Texture) are deliberately excluded and always stay live, applying on top of a baked or unbaked top surface identically, since they only ever touch the `0 .. num_top-1` prefix, same as the brush. A baked tile's pad/terrain/notch/path portion is a snapshot: it's only valid until something it was fit against changes (`_bake_signature` covers both the top-surface shape *and* every flora placement/terrain-object transform/path-feature point), at which point `rebuild_tile` silently reverts just that portion to live and prints a console notice — never silently misapplies stale geometry. The frozen brush contribution (`hf_baked_top_offset`) is a different, simpler case: it's a `num_top`-indexed z-delta with the exact same "survives height edits, dies on a vertex-count change" contract the live `hf_brush_disp` layer already has, so it's invalidated independently of (and less often than) the pad/terrain/notch/path portion.

- **GPU point overlays use `POINT_UNIFORM_COLOR`**: any `batch_for_shader(..., 'POINTS', ...)` must draw with a shader from `gpu.shader.from_builtin('POINT_UNIFORM_COLOR')`, never `UNIFORM_COLOR`. The latter ignores `point_size_set` on Vulkan/Metal, so the dots render invisibly. Enforced by `tests/test_gpu_point_shaders.py`.

### Token Usage Report (appended on `end plan`)
Counts come from the API `usage` object on each response — never self-estimate.
Aggregate across all requests made since the matching `plan` trigger:

- Input tokens (prompt): sum of `usage.input_tokens`
- Cache tokens: `cache_creation_input_tokens` + `cache_read_input_tokens`
- Output tokens (answer): sum of `usage.output_tokens`
- MCP / tool-call tokens: input+output of requests issuing tool_use/tool_result
- Web request tokens: input+output of requests invoking web tools
- Source-search tokens: input+output of requests doing code/file search
- Project files read: count of distinct files opened
- Total tokens: input + output + cache
